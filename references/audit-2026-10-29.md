# Audit — API Reality Guard 0.1.0 → 1.0.0

**Date:** 2026-10-29
**Scope:** the eight-file package as originally delivered (`SKILL.md`, `README.md`,
`LICENSE.txt`, `references/verification-protocol.md`, `scripts/inspect_project.py`,
`scripts/validate_skill.py`, `tests/test_inspect_project.py`,
`VALIDATION_REPORT.md`).

The original package was competent. The prose was careful, the security posture was
sound, and the limitations were stated rather than hidden. This audit records what
was nonetheless wrong, in order of severity, and what changed.

---

## Severity 1 — a validator that approves what it cannot read

**Location:** `scripts/validate_skill.py`, lines 36–37.

```python
name_match = re.search(r"^name:\s*([^\r\n]+)\s*$", frontmatter, re.MULTILINE)
desc_match = re.search(r"^description:\s*(.*?)\s*$", frontmatter, re.MULTILINE)
```

**What is wrong.** The validator parses YAML with regular expressions. This is the
single most common way a skill validator lies, and it is the exact defect that a
public 800-skill collection had to add a CI grep to prevent, after shipping 604
truncated descriptions out of 817.

**Impact.** A folded scalar (`description: >`) is read as the one-character string
`>`. The length check then measures the wrong string, or no string at all, and the
file is approved.

**Reproduction.** A `SKILL.md` whose description is 2000 characters of `A` in a
folded block, against a 1024-character limit:

```
$ python scripts/validate_skill.py
PASS: SKILL.md frontmatter and body are present.
PASS: Skill name matches the directory name.
PASS: Relative Markdown links resolve inside the skill directory.
PASS: Required support files are present.
PASS: Exactly one SKILL.md is present in the package.
$ echo $?
0
```

The real description is **2058 characters**, twice the limit. The validator reports
success.

A second, quieter failure rides along: `content.split("---", 2)` breaks on any
`---` occurring inside a frontmatter value, and `content.startswith("---\n")`
rejects a file whose first line ends in CRLF on a host that does not normalise
newlines.

**Fix.** `split_frontmatter()` finds delimiter lines rather than splitting on a
substring, tolerates a BOM and CRLF. `load_frontmatter()` parses with PyYAML when
available, and otherwise with a narrow reader covering plain, quoted and block
scalars that **raises** on anything it cannot classify. The degraded mode is
reported as a warning; it never silently substitutes a guess. A regression test
asserts that a 2000-character folded description is rejected.

## Severity 1 — a completeness claim that could be false

**Location:** `scripts/inspect_project.py`, line 155.

```python
for current_dir, dirnames, filenames in os.walk(root, topdown=True, followlinks=False):
```

**What is wrong.** `os.walk` with the default `onerror=None` silently swallows
`PermissionError`. A directory that cannot be listed simply disappears from the
walk.

**Impact.** The report sets `scan_truncated: false` and renders `Scan status:
COMPLETE` while having skipped an entire subtree. For a tool whose only job is to
give an agent facts, a false completeness claim is the worst failure available: the
agent concludes that a lockfile does not exist because it was never allowed to see
the directory containing it.

**Fix.** `onerror` collects `{path, reason}` into `scan_errors`; a new
`scan_complete` field is `false` when the walk was truncated *or* when any path was
unreadable; the CLI exits `1` in that case. A test asserts the behaviour on POSIX.

## Severity 2 — the tool cannot answer the question the skill asks

**Location:** `SKILL.md` rule 2 versus `inspect_project.py` in its entirety.

**What is wrong.** The skill's second non-negotiable rule is "distinguish declared
from resolved versions". The bundled helper cannot do that, by design: it reads
filenames only. The document is honest about this, but the result is a procedure
whose central step has no instrument behind it.

**Impact.** The agent is told to prefer lockfiles, and given a tool that lists a
lockfile's name. Every version claim then rests on the model's own reading of files
the tool refused to open — which is precisely the behaviour the skill exists to
prevent.

**Fix.** An opt-in resolution mode. `--package NAME` (repeatable) additionally reads
**allowlisted manifests and lockfiles only**, never source files, and returns
records carrying `authority` (`resolved` / `declared`), `confidence` (`exact` /
`best_effort` / `declared`), the source path and the line. Without `--package`, no
file content is read at all, so the strictest mode remains available.

Sixteen formats are supported. TOML uses `tomllib` on Python 3.11+ and a labelled
line scanner below that, so a hand-rolled parse can never masquerade as exact.

Verified on a real project:

```
$ python scripts/inspect_project.py ../mcp-driftguard --package pyyaml --json
"package": "pyyaml", "version": null, "constraint": "PyYAML>=6.0,<7.0",
"authority": "declared", "confidence": "declared", "source_path": "pyproject.toml"
```

A range, reported as a range. That is the correct answer, and the previous version
could not produce it.

## Severity 2 — the data model contradicts the workflow

**Location:** `inspect_project.py`, `EXACT_MARKERS` and the `manifests` output.

**What is wrong.** `kind` is a human sentence: `"Dependency lockfile"`. A machine
consumer that wants to apply rule 2 has to substring-match English prose to learn
whether a file is authoritative.

**Impact.** Either the agent ignores the distinction, or it re-implements it with
string matching — fragile, and invisible when it breaks.

**Fix.** Every marker now carries `authority` (`lockfile` / `manifest` / `tooling`)
and a boolean `is_lockfile`. The prose `kind` stays, for humans.

## Severity 2 — half of every compatibility question was missing

**Location:** `EXACT_MARKERS`.

**What is wrong.** The inventory recognised manifests and lockfiles, and ignored
runtime version files entirely: `.python-version`, `.nvmrc`, `.node-version`,
`.ruby-version`, `.tool-versions`, `rust-toolchain.toml`, `global.json`.

**Impact.** "Does this API exist in the version we run?" has two halves — the
library version and the runtime version. The tool only ever looked at the first.

**Fix.** A `runtime_markers` section, reading at most 4 KiB per file and reporting
the first version-like token, labelled as raw evidence rather than interpreted.

## Severity 3 — smaller defects, each with a concrete fix

| # | Defect | Fix |
|---|---|---|
| 1 | A file named `description` was classified as an R package manifest | Entry removed; R is detected by `renv.lock` |
| 2 | `files_scanned` counted FIFOs and sockets | `stat.S_ISREG` on `lstat`, so symlinks and special files are excluded before counting |
| 3 | The report embedded the absolute project path | The caller's own argument is echoed; a resolved absolute path is never invented |
| 4 | Exit `1` meant "truncated", undocumented anywhere | Contract documented in README and `SKILL.md`: `0` complete, `1` incomplete, `2` error |
| 5 | No `tool_version`, so a report could not be reproduced | `tool` and `tool_version` added; `schema_version` bumped to `2` |
| 6 | No conformance checks: angle brackets, reserved words, key allowlist | All three added to `validate_skill.py`, matching the agentskills.io rules |
| 7 | Scripts were never checked for syntax errors | `validate_skill.py` compiles every script in `scripts/` without writing bytecode |
| 8 | Six tests, none covering CLI contracts or failure paths | 58 tests, including exit codes, malformed lockfiles, oversized metadata and the folded-description regression |
| 9 | No CI, so `VALIDATION_REPORT.md` was a claim that would rot | GitHub Actions on three operating systems and three Python versions, plus a job that fails if regex frontmatter parsing is reintroduced |

## What was deliberately kept

- **The ten non-negotiable rules.** They are the product. Only rule 2 gained an
  instrument.
- **The evidence hierarchy.** Correct as written.
- **The refusal to invent evidence.** Preserved verbatim in spirit and in the labels.
- **The honest limitations section.** Extended, never softened.
- **No third-party runtime dependency.** The resolution mode uses `json` and
  `tomllib`, both standard library.

## What was deliberately not added

- **A JSON evidence ledger.** Tempting, and it would make the skill checkable by a
  script. It would also invite an agent to fill the schema with confident values to
  satisfy the shape. The Markdown table in the protocol is harder to fake and easier
  for a human to audit.
- **Automatic invocation of `pip show` / `npm ls`.** These execute the ecosystem's
  tooling. The skill tells the agent to run them; the bundled script never does.
- **Network documentation lookup from the script.** The prohibition is the point. The
  agent's own browsing tools are a separate, visible capability.

## Residual risk

1. **The agent may ignore the procedure.** Nothing in a skill can enforce compliance.
   The mitigation is that a missing evidence label is a visible omission, and the
   `SKILL.md` says so.
2. **`best_effort` parses can be wrong.** They are labelled, and the skill instructs
   the agent to confirm them with native tooling. A wrong label would be a real
   defect; a wrong unlabelled value is the defect this audit was written to remove.
3. **The confusable-name and semantic-equivalence problems** are out of scope here
   and belong to a different class of tool.
